## Proof Architecture and Ownership

`scripts/tests/consent-auth-local-proof.php` is an explicitly invoked developer CLI proof, not an installed HTTP action, plugin bootstrap, public route, browser login or CI database task. It validates exact root realpath, current LocalWP metadata/DB host/port/name and actual siteurl before creating fixtures. Multisite, persistent cache and custom database/cache drop-ins reject. Three randomly scoped `wp_alynt_auth_probe_{12 hex}_{options|users|usermeta}` tables must be absent before empty structure-only cloning; actual rows are never copied. An owner token gates child access; all three in-process `$wpdb` pointers move together before loading core auth APIs. An invocation-local query fence permits ordinary single-table writes/column inspection only to those owned tables and remains through shutdown. It is a defense against unintended core queries in this fixed harness, not a general-purpose SQL parser or a sandbox against same-privilege code.

Core loading retains genuine `WP_User`/`WP_Roles`, `WP_Session_Tokens`/`WP_User_Meta_Session_Tokens`, cookie generation/validation, current capability mapping and nonce creation/verification. Required default auth-hook callbacks are checked instead of removing them or stubbing functions. Minimal fixture roles, three synthetic users with random hashed passwords, and hashed core session verifiers live only in owned tables. Cookie/token/nonce values stay in CLI memory; no `wp_set_auth_cookie`, email, web route, production plugin or remote operation is invoked. Public origin is fixture-only; existing wp-config constants are read by core, never changed or exported.

The unchanged dormant request adapter receives core authorize/nonce/UUID ports plus real closed schema-5 SQL context/receipt observation. Every authorize call validates the cookie/session afresh, clears only process-local fixture user/meta caches, rereads role/capability facts and requires fixed synthetic site scope plus `manage_options`. A cached current user or valid nonce alone is not admission. Context remains ineligible; the real closed model rejects all commands. Additional guard/acknowledgement cases use a clearly labeled **harmless observation fixture receipt**, never the consent ledger or authenticated provenance. Its `committed` result acknowledges only that probe-row insert, not consent, schedule, scan, queue, upload or rollback.

`lifecycle-proof-safety.php` shares the existing read-only option/user digests and assertions between the two explicit entrypoints. Existing lifecycle/ledger/provenance case logic is unchanged. New helpers separate storage fencing, core loading/fixture accounts, auth ports, primary denials, guard interleavings and receipt/child cases. CI adds PHP syntax checks only; supported PHP unit/lint/build policies remain intact. No production definitions, dependencies, generated assets, versions, test assertions or skips are changed.

The reviewed proof passed **28 checks**, covering:

- Query-filter denial of actual-table writes without submitting any such query; guest, GET and real subscriber capability denials before closed-state/private receipt reads.
- Genuine admin cookie/session/capability validation with server-issued non-admitting intent; grant/rebind refusal and unchanged closed permission bytes.

Core nonce verification can remain valid after session revocation; fresh session validation still rejects. Role loss is exercised by changing only the fixture account's role, not removing a direct capability that is still inherited from its role.
- Actual core nonce expiry using a process-local two-second `nonce_life` filter and bounded tick observation (at most five seconds), restored afterward. The separate 300-second command deadline uses the injected server clock; core nonce longevity cannot extend it.
- Per-write guard rejection on session revocation, capability loss during context observation, deadline expiry and a separately seeded valid closed epoch change. A retained guard is inactive after return and performs no later SQL work.
- One harmless guarded observation receipt and duplicate observation without changing consent; expired command cannot reach its sink, while a freshly reauthenticated read nonce may observe that same ID without renewing it. Guest/subscriber cannot read it; archived fixture IDs cannot be promoted by real authorization.
- An independent PHP child authenticates through core, commits only a harmless owned receipt, and waits after its marker. Parent termination before acknowledgement is followed by fresh real authorization/receipt observation with no sink replay. Raw cookie/nonce/token is never a child argument or stored receipt field.
- Real authorization cannot initialize missing safety storage. Final authority/consent remain false and authenticated grant/receipts absent; activation/rollback remain unavailable.

## Development Failures and Cleanup Review

Early runs correctly stopped at an overly narrow fence that initially rejected WordPress's read-only `SHOW FULL COLUMNS` inspection; only owned-table metadata reads were added. Partial core loading exposed required KSES, footnote and REST cookie-status callbacks. Genuine core files were loaded and dependency preflight added; no callback/security check was removed. An initial cleanup-context exception left three empty/owner-only tables; bundled MySQL preview identified the exact parent-created scope, confirmed its owner marker and **1 total row**, removed those exact tables, and independently verified actual rows unchanged. Cleanup now catches partial-core current-user reset failure, attempts each owned table's readable preview/drop independently and never treats a failed absence query as successful verification.

Further failures corrected fixture semantics, not runtime expectations: role-inherited capabilities require an actual fixture role change to test loss; state reseeding/restoration must preserve core's original non-autoload label as well as exact permission bytes. Existing assertions remain strict. All failed-run fixture scopes were cleaned, with final independent zero-table reconciliation. One bootstrap fatal diagnostic was appended to LocalWP's existing debug log before cleanup hardening; it contains the missing-callback error/source stack, not auth values. That existing log was not edited or truncated. Subsequent database failures are explicitly reported through bounded proof checks without raw SQL/private payload logging.
