Two new test-loaded definitions, `includes/class-closed-consent-provenance-store.php` and `includes/trait-closed-consent-provenance-validation.php`, implement a strict schema-5 closed checkpoint. The final class extends the existing dormant safety store; private aliases reuse unchanged schema-2/3/4 validators and original fixture receipt digest semantics. It does not inherit the fixture ledger's grant transition implementation.

Construction takes an explicit fixed site UUID, in-memory CAS backend, fixture clock and literal switch defaulting off. It invokes no readers/guards and creates no identity/storage/hooks. Default/false/truthy/invalid scope stays zero-read dormant. The generic backend/guard are explicit test seams, not a production sandbox or real authorization; no site/database-backed instance is created here.

Public `prepare_closed(binding, expected_generation, guard)` is an explicit guarded migration; `snapshot()` is private-model observation and `receipt(domain, id)` is bounded namespace observation. `command()` rejects every grant/revoke/rebind/activation/rollback request without reading or invoking its guard. Inherited initialization/claim/transition/invalidation also remain zero-read denied. No HTTP/permission handler or execution API is installed. The checkpoint is intentionally immutable after migration: real consent, closure commands, rebind, recovery and journal writers need separately reviewed contracts, not a hidden method to modify it.

## Exact Closed Schema and Archival Provenance

Schema 5 retains the eight schema-3 root fields plus `provenance`. Its exact six-field provenance is fixed `site_uuid`, source `closed_migration_fixture_v1`, `authenticated_grant: null`, `authenticated_receipts: []`, `legacy`, and `migration`. Any grant, nonempty authenticated receipt, authenticated-looking source, unknown field or active/consenting/enabled authority state rejects. This private version is not a deployed option/schema upgrade or public/wire contract.

The exact legacy archive contains original schema version, storage generation, binding, schedule revision, original lifecycle, nullable complete schema-4 ledger and a canonical consistency digest. Schema 3 requires a null archived ledger. Schema-4 source/last receipt/history/grant pointer and their original `adb-consent-fixture-command-v1` digests are preserved without relabeling, pruning or rewriting. Synthetic archived consent may still be true, but current consent is always false and authenticated provenance always absent. The archive is expressly untrusted and never an admission projection.

Journals/authority/due/dispatch stay in the unchanged root rather than being duplicated. The validator reconstructs the source from those fields and archival metadata, runs the original strict validator, rejects unfinished source work, and checks a fixed root-order `adb-closed-migration-fixture-v1` digest over complete source contents/site scope. This detects inconsistent archival/protected-data edits; it is not a signature or protection against same-privilege writers who can recompute hashes. Full internal snapshots contain private archival data and must not be exported through status/support UI.

The migration record has exactly original expected permission generation, resulting generation and commit time. All three current monotonic counters must equal their source value plus one; current lifecycle is exactly the old lifecycle with consent false, disabled phase, incremented epoch and recorded commit time. Old history remains new-model/unknown; no never-activated, authenticated issuer or verified handoff fact is inferred from a migration receipt. Older schema-3/4 readers are unchanged and reject schema 5 rather than interpreting it as authority.

## Explicit Migration, Capacity and Failure

Migration accepts only strict existing schema 3/4 in the dedicated non-autoloaded state row with matching binding and original submitted epoch. It never creates absent storage/identity, repairs corrupt state, accepts unsupported versions/autoloaded rows, or migrates on getters/requests/startup. Every unfinished claim or nonterminal dispatch blocks migration even after expiry; nothing resolves, deletes or reassigns uncertain work to make migration pass. Terminal/native journals, due, cadence, dispatch and original history remain unchanged.

The guard must return literal true before each authoritative read and immediately before each attempted write; malformed/truthy/throwing guards are denied/redacted. Validate positive bounded nonregressing UTC, original epoch/context, strict source and capacity before building one conditional successor write. Recheck the fixture clock after the final guard and record a later valid write time; regression, invalid type or overflow rejects. This is a scoped fixture check, not proof of actual WordPress authentication or a capability/database transaction.

At most three exact-byte CAS attempts are allowed. A competing migration/fixture closure that changes epoch wins; the loser rereads only to reject the original stale request, never to adopt the winner's epoch. Matching schema-5 preparation at its current epoch is observation-only and cannot reset archive/counters/provenance. A lost acknowledgement may leave a committed successor even when preparation returns an error; reconcile by a fresh valid snapshot/current-epoch observation, not by claiming the error disabled the old grant or blindly repeating a stale migration.

Keep original 128 KiB/depth-16/50-journal bounds and the legacy limit of 50 history receipts plus its last slot. No authenticated receipts are accepted. Migration leaves 4096 encoded bytes and one further increment in all three counters for a future separately implemented closure contract; insufficient reserve/encoder failure rejects without overwrite, never pruning to fit or resetting counters. Tests retain a full 50-receipt history plus last receipt and native terminal journal under the reserve. No command implementation uses that reserved capacity here, and physical/database availability is not guaranteed.

Failed definitive fixture writes retain exact original bytes and synthetic grant; they are not a successful disablement. Error/nonboolean/throwing or committed-then-failed acknowledgements are redacted as unresolved/stale as applicable. Independent snapshot observation can distinguish a valid closed checkpoint after a known fixture commit. Fixed `schedule_safety_provenance_*` errors disclose no stored payload/SQL/path/auth exception. The pure transformed state performs no nonce issuance, logging, settings/connection/queue/cron effect or external callback.

## Namespace and Request-Adapter Integration

Receipt observations accept only `fixture_intent_v1` and `fixture_request_v1` with strict UUIDs. A retained legacy identity is always `observed_superseded` within its original fixture-intent namespace because migration advanced the epoch. Reusing that identity in the request namespace returns a domain conflict, never an authenticated duplicate/grant. Unknown identities are `not_found`, not evidence that no earlier write occurred. Unsupported/authenticated namespace labels reject before reading. All observations have explicit fixture source and dispatch/execution false.

Five new test classes and one shared fixture use real model validation/CAS over in-memory rows. Request integration reuses the unchanged dormant request adapter with model-backed context/receipt ports: context advertises eligibility false, authenticated grants never issue, commands never execute/migrate, and authorized request reconciliation cannot relabel a legacy grant. Denied requests do not read the successor; issuance against unmigrated state does not prepare storage. These are in-memory ports, not installed production providers or real WordPress sessions.
