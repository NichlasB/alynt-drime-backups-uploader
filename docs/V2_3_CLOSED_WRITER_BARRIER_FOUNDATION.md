No global option/cron filter, route, callback dispatcher, new dependency or actual settings writer is installed.

The final store extends only the dormant base safety store, reusing unchanged schema-2/3/4/5 validation through private aliases. It does not inherit ledger grant commands. The `SOURCE` constant is retained solely for the embedded old checkpoint validator; current provenance uses the distinct `BARRIER_SOURCE = closed_writer_fixture_v1`. Neither a constructor switch, injected guard, source label nor opaque hash is administrator authorization. The generic CAS/guard are test seams, not a production sandbox; this task instantiates only the existing in-memory backend.

Literal enablement defaults off with a fixed existing fixture UUID and UTC clock. Disabled/truthy/invalid scope performs zero reads/writes/guard calls. `command()` rejects grant/revoke/rebind/activate/dispatch/rollback without reads or guard calls. Inherited initialization/claim/journal transition/invalidation also reject; no activation API exists. Explicit APIs are `prepare_closed(binding, expected_epoch, guard)`, `begin(command, guard)`, `finish(command, guard)`, `abandon(command, guard)`, private-model `snapshot()` and bounded fixture `receipt(domain, id)`. Snapshots are not public status/support output or admission projections.

## Strict Closed Schema 6 and Frozen Origin

Private fixture schema 6 keeps the eight model/lifecycle root fields plus `barrier`, replacing root `provenance`. This is not a deployed option or public/wire schema. The exact ten barrier fields are `site_uuid`, `source`, `checkpoint`, `upgrade`, `authenticated_grant`, `authenticated_receipts`, `pending`, `closure`, `completion` and `receipts`. Authenticated grant is always null, authenticated receipts always empty, authority false, consent false and lifecycle disabled. Real authenticated grant provenance would require a separately reviewed version/contract, not relaxing this validator or changing its fixture label.

The complete decoded schema-5 checkpoint is frozen once and independently validated through its original strict validator. It retains all old lifecycle/provenance/receipt history without promotion or recursive successor archives. Current binding, claims, authority/cadence/due and dispatch equal the checkpoint exactly; unknown history stays unknown. JSON re-encoding is not a promise to preserve original whitespace bytes. A domain/site-scoped checkpoint digest is consistency checking only, not a signature against equally privileged writers.

`upgrade` has exactly checkpoint digest, original expected permission generation, result generation and commit UTC. Explicit existing-row schema-5 upgrade advances storage generation, schedule revision and permission generation once. Older/missing/unsupported/corrupt/autoloaded state rejects without initialization, UUID creation, repair or automatic schema-3/4 migration. Every unfinished source journal/dispatch is rejected and preserved, including expired uncertainty. A matching schema-6 observation at its current epoch never resets a pending writer, archive or receipt; stale original epoch rejects. Lost acknowledgement can leave a committed successor despite an error; observation does not replay the upgrade.

This foundation cannot create or mutate owned scan work. It preserves existing terminal/native journals verbatim and retains pending *writer* uncertainty separately while consent stays false; it does not implement the future active-work draining validator, claim/start/effect fences or handoff history. Rejecting an unfinished origin is not proof that work stopped.

## Fixture Intents, Immutable Receipts and Fencing

A begin intent has exactly `command_id`, `site_uuid`, `enrollment_binding`, `expected_generation`, `kind`, `target`, sorted unique `fields`, `before_hash`, `after_hash`, `issued_at`, `expires_at`. Current allowlists are settings patch (`auto_scan_enabled`, `scan_interval`) or connection patch (`action_key_id`, `dashboard_origin`, `remote_actions_enabled`, `status_endpoint_enabled`). These are field *names*, never values. No arbitrary option/table target, credentials, raw settings delta, posted issuer/provenance or executable callback is stored. Equal before/after hashes reject rather than renewing permission. The server-issued/authenticated boundary for these fixture envelopes is not implemented.

Finish/abandon have exactly fresh `command_id`, original `operation_id`, site/binding, expected current epoch, original `closure_generation`, `observed_hash` and intent times. IDs cannot equal the referenced operation or collide with retained archived fixture IDs. All commands require strict scalar types, fixed scope and bounded positive UTC with at most 300 seconds; original identity/epoch/deadline is never refreshed by contention. Finish retains the begin intent's original times and requires its after-hash. Explicit abandon requires an intent issued no earlier than closure commit and a before/after hash observation; expiry alone cannot abandon. All such hashes are untrusted fixture observations, not proof of a real secondary write or permission to perform one.

| Model transition | Atomic state-only result; no secondary write |
| --- | --- |
| Begin | CAS an immutable closure receipt and pending operation ID; advance all three counters. Another pending writer blocks new begin. No target/context mutation, callback or grant. |
| Finish | With exact pending owner, closure/current epoch, original time window and matching fixture hash, CAS separate immutable completion plus pending removal; advance all counters. Original closure receipt stays unchanged. |
| Abandon | Fresh guarded exact-owner/epoch fixture inspection records a distinct abandonment completion; advance all counters, keep consent false. Never replay an intended write, clear other work or infer cancellation from elapsed time. |
| Duplicate / superseded | Under valid original intent, same ID/digest observes current/superseded receipt only. Changed purpose/digest conflicts; expired consumption rejects even if retained. Receipt observation neither renews the command nor unblocks pending. |
| Failed / ambiguous acknowledgement | Return a redacted error or a later exact observation, never claim disablement or no commit. Definitive failed terminal writes preserve pending. A known fixture commit with lost acknowledgement is reconciled by original receipt, not effect replay. |

Receipts contain exactly purpose, complete bounded fixture command, canonical domain/purpose digest, result epoch and commit time. Each result is expected + 1; the validator checks a contiguous monotonic begin/terminal chain from the upgrade, original closure references, unique IDs/epochs and nonregressing commit times. No missing history, fabricated completion, changed pending pointer or counter reset is accepted. Current closure/completion are separate mandatory slots; previous pairs move into bounded immutable history. Closed counters track checkpoint values plus the same permission delta.

At most three exact-byte CAS attempts; literal fixture guard before every read and write attempt; final clock/deadline recheck. The clock is checked again after candidate encoding/validation immediately before CAS: expiry or a changed prepared timestamp rejects conservatively, never extends intent or commits an earlier timestamp. A loser reobserves only its original request, not a winner's new epoch. Callback/read/write exceptions are fixed `schedule_safety_barrier_*` errors with no payload, SQL, path or private provider details. Successful `committed` acknowledges **only this model's safety-row CAS**, not target settings, real consent, a scan, queue/upload or transaction. No client-side check certifies deadline-at-physical-SQL-commit or atomic WordPress privilege revocation.

Fixture receipt observation supports only `closed_writer_fixture_v1` and archived `fixture_intent_v1`. Retained cross-domain ID reuse conflicts; archived receipts remain superseded and untrusted. Authenticated and old request namespaces reject before reading. Results expose exactly outcome, fixture source and false dispatch/execution flags. The store has no real request authorization boundary: any future private receipt reader must authenticate before calling it.

## Capacity, Failure and Scope Limits

The encoded row remains at most 128 KiB, JSON depth 16; each new receipt at most 1024 bytes. Upgrade and pending begin preserve 4096 encoded bytes for mandatory terminal state and counter growth. The combined optional history budget is 50 across frozen fixture history and new history; frozen last receipt and current closure/completion remain mandatory and byte-bounded. No pruning/compaction/eviction or scope reset. A full history can block another begin but cannot consume the current operation's reserved terminal slot. Actual worst-case frozen-origin duplication is tested to reject without discarding journals/history.

Upgrade requires four increments of source headroom (upgrade, begin, terminal, one further closure). Begin requires three (begin, terminal, reserve); terminal requires two (terminal, reserve). Validators require remaining reserve for initial/pending/terminal states. No overflow/wrap/epoch reset. If headroom is exhausted, state stays closed and a new operation rejects. Byte/count/counter reserve cannot guarantee physical persistence during storage outage.

Eight new test classes plus one shared fixture cover closed transitions, malformed commands/state, namespace separation, history/byte/counter bounds, protected journals/due/other rows, concurrent begins, finish-versus-abandon, delayed finisher after abandonment/new begin, A-to-B-to-A opaque hashes, guard/clock/deadline failures, read/write failure and committed-then-lost acknowledgement. Initial scaffolding lacked definitions as expected; one malformed-state test was corrected to keep its command valid instead of copying the intentionally corrupt epoch into that command. Rejection assertions stayed strict. PHPCBF formatted only new definitions; no existing tests/assertions/skips or lint thresholds changed.

These are deterministic in-memory state interleavings, **not** SQL locks, multi-process durability, real WordPress authentication, conditional target writes, actual ABA-fenced settings providers or power-loss proof. In particular, calling `finish()` after an external write would leave a check-to-effect race: it is not the separately designed same-connection locked target/completion transaction. An old paused target writer is not cancelled by rejecting its later receipt. Production effects/entry points, persistent cache, lifecycle/downgrade/uninstall/restore, real authenticated provenance and actual activation remain unproved. No full feature/pre-release clearance, package, release or deployment is claimed. Versions stay uploader `0.5.25`, dashboard `0.1.77`.
