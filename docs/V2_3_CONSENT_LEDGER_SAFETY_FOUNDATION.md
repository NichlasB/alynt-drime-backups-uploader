## Exact Internal Schema And Migration

The private successor is **schema 4**, confined to fixture memory here. Root keys are the existing eight schema-3 keys plus `ledger`. Reuse schema-2 journal/authority/dispatch validation and the conservative schema-3 lifecycle checks: authority always disabled, only preparing/draining/disabled, history only new-model/unknown, and every unfinished journal/nonterminal dispatch requires draining with consent false. No field claims authenticated provenance, activation or verified handoff.

The exact five-field ledger holds fixed `site_uuid`, source `fixture_intent_v1`, nullable `grant_command_id`, nullable `last_receipt` and a bounded `receipts` map. The source marker deliberately rejects authenticated-looking/other source labels. It records synthetic intent provenance only. A future authenticated writer must not bless fixture grants by interpreting this marker or boolean differently; real authorization/provenance needs its own reviewed transition/version decision.

Explicit preparation accepts only an existing strict schema-3 row with matching binding and submitted permission epoch. Missing/corrupt/autoloaded/unsupported/older state is not created, normalized, repaired or migrated implicitly. All unfinished migration is rejected, even after expiry. Preserve terminal legacy/native journals and dispatch, cadence/due and history verbatim. In one CAS, advance storage generation, schedule revision and permission generation; close consent, use disabled phase and initialize empty fixture receipts. A synthetic schema-3 grant never becomes successor consent. Preparation of existing matching schema 4 is observation-only at its current epoch and cannot erase a grant/receipt; stale submission rejects rather than refreshing itself.

The currentness precondition is explicit. Simultaneous preparation yields one accepted migration; the losing old epoch rejects. Committed-but-unacknowledged migration can be read on restart without reapplying. No never-activated/handoff evidence is inferred from an empty ledger, migration or history label. Older schema readers continue rejecting schema 4 rather than promoting or downgrading it.

## Synthetic Command And Receipt Contract

Each intent has exactly eight scalar fields: `command_id`, `purpose`, `site_uuid`, `enrollment_binding`, `expected_generation`, `issued_at`, `expires_at`, `replacement_binding`. Strict UUID/lowercase hash/integer rules reject coercion, unknown keys and posted actor/trusted/nonce assertions before any storage read. Purpose is grant/revoke/rebind only. Grant uses a positive bounded issuance/expiry window of at most 300 seconds, requires now within it and no replacement binding. Closure times must be zero and do not rely on a live grant window or remote pairing. Rebind requires a distinct valid replacement hash. These injected times are synthetic, **not proof of a server-issued or nonce-bound intent**; no real issuance/authentication handler exists here.

Digest uses a fixed ordered field sequence and `adb-consent-fixture-command-v1` domain, independent of incoming array order. It is not a signature or secret. Each exact four-field receipt contains the validated command, canonical request hash, result generation and committed UTC time. Validators verify command hash, expected/result generation increment, grant window at commit, site/context match, unique retained receipt generations and linkage to current lifecycle epoch/time. Current grant points to the latest grant receipt; closed states have no grant pointer. Internal snapshots include private model data and must never be exported as support/status payloads.

One fresh command atomically records receipt, advances all three monotonic counters and changes preparing consent or closure. Grant rejects existing consent and unfinished work, does not refresh a grant and leaves authority disabled. Revoke/rebind clear consent and preserve uncertain journal/dispatch records under their original owner/binding, without expiring/resolving/replaying them. A rebind changes only the model's binding in the same closed CAS; it does not mutate any actual enrollment option. New consent for the new binding requires a fresh explicit synthetic command, not inheritance.

Exact retained duplicate is observation-only, even after the grant intent expires or model restarts. Same retained identity/different canonical intent conflicts. Retained old grant after closure/rebind is observed superseded, never regranted. Missing older receipt still cannot authorize an old epoch/binding. Receipt lookup precedes stale binding/expiry checks so a retained closed rebind can be observed with its original command; this is an internal fixture behavior, not permission to bypass authentication on a future request.

Every success result has only `outcome` (committed/observed-current/observed-superseded), `dispatch_supported: false` and `execution_supported: false`. No current permission projection, owner, receipt, hash, site identity, clock or private failure is returned. No observer or public error-code vocabulary changes. Failures use fixed redacted schedule-safety ledger codes; unknown outcome is not a no-write guarantee.

## Bounds, Capacity And Failure Semantics

State retains the existing 128 KiB/depth-16/50-journal limits. Each receipt is at most 1024 encoded bytes; history has at most 50 entries plus one always-present latest transition slot once commands begin. Migration and grant leave 4096 encoded bytes of closure reserve. Grant leaves a history slot to retain the grant being closed; history exhaustion rejects new grants rather than evicting records. Closure archives its previous grant, but may omit archiving a superseded closure when optional history/byte capacity is unavailable. It always persists its own latest receipt and retains existing history. No pruning/deletion routine is implemented; eventual history-retention policy remains a later review, not invented here.

Before migration/grant, all three counters have headroom for the transition and one subsequent closure. Closure checks one remaining increment, never wraps/resets counters. Once the final usable generation is reached, state stays closed and fresh commands reject; exact duplicate remains observation-only. A grant-bearing state itself is invalid if its byte/counter/history closure reserve has been lost. The population test combines 50 terminal journals and 48 retained receipts, confirms reserve and successfully closes without losing journals. These are bounded model guarantees, not proof of disk/database availability.

CAS retries are bounded at three and reread the original submitted epoch/binding on each attempt; they never adopt a new epoch. Concurrent closure/rebind winning before grant rejects stale grant; identical competing command is observed once after reload. The transform has no clock reads, callbacks, external logging, settings writes or effects. Clock/provider/backend Throwables and error/non-boolean persistence acknowledgements are redacted. If a backend reports false after committing, a fresh receipt observation can reconcile without a second write; unreadable or otherwise unresolved outcomes do not report success. A definitive fixture write failure leaves exact bytes unchanged; failed closure retains the old synthetic grant rather than reporting disabled.

This ledger does not make independent settings/enrollment writers atomic, fix stale timestamp whole-option writers, authenticate users, prove fresh real providers, cancel started PHP/queue/upload work or close the check-to-effect race. Current schema-4 grant cannot activate production or verified legacy behavior. Normal production legacy behavior and existing upload/abort/retention permission remain unchanged. Actual schema migration, emergency stop, real grant/revoke and lifecycle recovery must pass separate approvals/proofs.
